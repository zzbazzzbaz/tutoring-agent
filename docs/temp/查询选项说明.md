# LightRAG 查询选项说明

> LightRAG WebUI 查询页面的三个选项对应检索流水线的三个截断点。

## 流水线全貌

```
用户查询 "物理层有什么传输介质"
  │
  ├─ ① 检索阶段
  │    从知识图谱 + 向量库找出相关内容
  │    -> 实体（物理层、双绞线、光纤...）
  │    -> 关系（双绞线 → 导引型传输介质）
  │    -> 原文片段（Document Chunks）
  │
  ├─ ② 拼接阶段
  │    把检索结果 + 系统指令 + 用户问题拼成一个完整 prompt
  │    -> "你是一个AI助手...以下是知识图谱数据...用户问题：物理层有什么传输介质？"
  │
  └─ ③ 生成阶段
       把完整 prompt 发给 LLM（qwen3.6-flash），生成最终答案
       -> "物理层涉及的传输介质主要分为两大类：导引型和非导引型..."
```

## 三个选项

| 选项 | 在哪一步截断 | 返回内容 | 调 LLM 吗 |
|---|---|---|---|
| **仅需上下文**（only_need_context） | ① 之后 | 实体 + 关系 + 原文片段 | 否 |
| **仅需提示**（only_need_prompt） | ② 之后 | 拼好的完整 prompt 文本 | 否 |
| **不勾选**（默认） | ③ 完成 | LLM 生成的最终答案 | 是 |

---

### 1. 仅需上下文（only_need_context=True）

**返回**：检索到的原始内容，包括三部分：

- **Knowledge Graph Data (Entity)**：实体名称、类型、描述
  ```json
  {"entity": "物理层", "type": "concept", "description": "OSI参考模型的最底层..."}
  {"entity": "双绞线", "type": "artifact", "description": "最常用的导引型传输介质..."}
  ```

- **Knowledge Graph Data (Relationship)**：实体间关系
  ```json
  {"entity1": "双绞线", "entity2": "导引型传输介质", "description": "双绞线是导引型传输介质的一个具体实例。"}
  ```

- **Document Chunks**：原文片段（带 reference_id 引用）
  ```json
  {"reference_id": "1", "content": "# 物理层\n\n## 传输介质\n\n传输介质分为导引型和非导引型..."}
  ```

**用途**：把检索结果交给自己的 Agent 处理。教学 Agent 用这个选项拿到知识上下文，然后用苏格拉底式追问生成回复。

**API 调用**：
```python
resp = requests.post("http://101.35.223.219:15434/query", json={
    "query": "物理层有什么传输介质",
    "mode": "hybrid",
    "only_need_context": True,
}, headers={"X-API-Key": "lightrag-sk-teaching-agent-2026"})
# resp.json()["response"] 是检索到的上下文文本
```

---

### 2. 仅需提示（only_need_prompt=True）

**返回**：LightRAG 拼好的完整 prompt 文本，即"准备发给 LLM 但还没发"的内容。包含：

- **---Role---**：系统角色定义（"你是一个AI助手..."）
- **---Goal---**：任务目标（"基于知识库生成回答"）
- **---Instructions---**：步骤指令（如何提取信息、组织回答、生成引用）
- **---Context---**：检索到的实体 + 关系 + 原文片段（同"仅需上下文"的内容）
- **---User Query---**：用户的原始问题

**用途**：调试 LightRAG 的 prompt 模板。检查上下文是否完整、指令是否合理、格式是否正确。**生产环境不用这个选项。**

---

### 3. 不勾选（默认模式）

**返回**：LLM 生成的最终答案，基于检索到的上下文回答用户问题。

**示例回答**：
> 物理层涉及的传输介质主要分为两大类：导引型传输介质和非导引型传输介质。
> 1. 导引型传输介质：双绞线、同轴电缆、光纤
> 2. 非导引型传输介质：无线电波、微波、红外线
> ...
> References: [1] 物理层.md

**用途**：测试完整 RAG 效果。LightRAG 自己检索 + 自己生成答案，端到端验证。教学 Agent **不用这个**，因为 LightRAG 生成的是"百科式"答案（直接给答案），而教学 Agent 需要"苏格拉底式"答案（追问引导）。

---

## 教学 Agent 用哪个

**用"仅需上下文"（only_need_context=True）。**

```
学生提问
  → 你的 FastAPI 调 LightRAG API（only_need_context=True）
  → 拿到实体 + 关系 + 原文片段
  → 把上下文塞进引导 Agent 的 prompt
  → Agent 生成苏格拉底式追问回复
  → 返回给学生
```

原因：LightRAG 擅长检索（双层检索 + 图谱遍历），但不擅长教学（苏格拉底式追问）。只取检索结果，答案交给你的教学 Agent 生成。

## API 参数对照

| WebUI 选项 | API 参数 | 值 |
|---|---|---|
| 仅需上下文 | `only_need_context` | `true` |
| 仅需提示 | `only_need_prompt` | `true` |
| 不勾选 | （不设或设 false） | `false` |

> 注意：`only_need_context` 和 `only_need_prompt` 不能同时为 `true`。如果都设为 `true`，LightRAG 优先返回上下文（`only_need_context`）。

# 查询模式与检索参数说明

## 查询模式：决定"从图谱里检索什么"

LightRAG 的知识图谱有两种元素：**节点（实体）** 和 **边（关系）**。

```
知识图谱:
  节点(实体): "物理层"、"双绞线"、"光纤"、"传输介质"...
  边(关系): "双绞线->导引型传输介质"、"物理层->电气特性"...
```

### 五种模式

| 模式 | 检索节点 | 检索边 | 检索原文 | 适合什么问题 |
|---|---|---|---|---|
| **local** | ✅ | ❌ | ✅ | "什么是双绞线" -- 查具体实体 |
| **global** | ❌ | ✅ | ✅ | "双绞线和光纤有什么区别" -- 查实体间关系 |
| **hybrid** | ✅ | ✅ | ✅ | "物理层有什么传输介质" -- 实体+关系都要 |
| **naive** | ❌ | ❌ | ✅ | 传统 RAG baseline，不用图谱 |
| **mix** | ✅ | ✅ | ✅ | 最全面（图谱+纯向量），最慢 |

**推荐**：教学 Agent 用 `hybrid`。既查具体知识点（实体），又查知识点间的关联（关系）。

---

## 图谱检索逻辑（以 hybrid 为例）

```
用户查询: "物理层有什么传输介质"
  │
  ├─ ① LLM 提取关键词
  │    低层关键词(具体实体): ["物理层", "传输介质"]
  │    高层关键词(主题概念): ["传输介质分类", "导引型", "非导引型"]
  │
  ├─ ② 向量匹配
  │    低层关键词 -> 匹配实体节点向量
  │      -> "物理层"(0.92), "传输介质"(0.88), "双绞线"(0.85)...
  │      -> 取前 KG Top K 个（默认 60）
  │
  │    高层关键词 -> 匹配关系边向量
  │      -> "双绞线->导引型传输介质"(0.90), "传输介质->导引型"(0.87)...
  │      -> 取前 KG Top K 个（默认 60）
  │
  ├─ ③ 图遍历（1跳扩展）
  │    "双绞线" 的邻居节点 -> "非屏蔽双绞线", "屏蔽双绞线", "xDSL"
  │    "传输介质" 的邻居节点 -> "导引型", "非导引型", "光纤", "同轴电缆"
  │    -> 把邻居也加入候选集
  │
  ├─ ④ 收集关联原文
  │    "双绞线" 关联的 chunk -> 原文片段 #2（传输介质章节）
  │    "光纤" 关联的 chunk -> 原文片段 #2
  │    -> 取前 Chunk Top K 段（默认 20）
  │
  ├─ ⑤ [可选] 重排
  │    reranker 模型对所有候选重新打分，保留最相关的
  │    （当前未配置重排模型）
  │
  ├─ ⑥ Token 截断
  │    实体描述: ≤ max_entity_tokens（默认 6000）
  │    关系描述: ≤ max_relation_tokens（默认 8000）
  │    原文片段: ≤ 剩余预算（默认 30000 - 6000 - 8000 = 16000）
  │
  └─ ⑦ 返回上下文
       -> 实体: 物理层, 双绞线, 光纤, 同轴电缆...
       -> 关系: 双绞线->导引型, 传输介质->非导引型...
       -> 原文: "# 物理层\n\n## 传输介质\n\n传输介质分为..."
```

### 返回的是节点还是边？

**都返回**（hybrid 模式下）。返回的上下文包含三部分：

```
Knowledge Graph Data (Entity):       ← 节点（实体）
  {"entity": "物理层", "type": "concept", "description": "OSI参考模型的最底层..."}

Knowledge Graph Data (Relationship): ← 边（关系）
  {"entity1": "双绞线", "entity2": "导引型传输介质", "description": "双绞线是导引型..."}

Document Chunks:                     ← 原文片段
  {"reference_id": "1", "content": "# 物理层\n\n## 传输介质..."}
```

## 各模式检索逻辑对比

### local 模式
```
查询 -> 提取低层关键词 -> 向量匹配实体节点 -> 1跳邻居 -> 关联 chunk
不查关系边
适合: "什么是双绞线"（查具体实体）
```

### global 模式
```
查询 -> 提取高层关键词 -> 向量匹配关系边 -> 1跳邻居 -> 关联 chunk
不查实体节点
适合: "双绞线和光纤有什么区别"（查实体间关系）
```

### hybrid 模式
```
local + global，实体节点和关系边都查，合并去重
适合: "物理层有什么传输介质"（既要具体实体，又要关系分类）
```

### naive 模式
```
跳过图谱，直接向量检索 chunk 原文
适合: 传统 RAG baseline 对比
```

### mix 模式
```
hybrid + naive，图谱检索 + 纯向量检索，最全面
适合: 追求最高检索质量，不在乎速度
```

## 检索参数详解

### KG Top K（默认 60）

知识图谱检索数量上限。不同模式下含义不同：

| 模式 | KG Top K 含义 |
|---|---|
| local | 检索 60 个**实体节点** |
| global | 检索 60 条**关系边** |
| hybrid | 检索 60 个实体 + 60 条关系（共 120 个） |
| naive | 不适用（不查图谱） |

值越大检索越全，但上下文越长、LLM 处理越慢。

### 文本块 Top K（Chunk Top K，默认 20）

从向量库检索原文片段的数量上限。每个 chunk 约 1200 tokens，20 个 = 最多 24000 tokens 原文。

### 实体词元数上限（max_entity_tokens，默认 6000）

最终传给 LLM 的上下文里，实体描述部分最多占 6000 tokens（约 3000 汉字）。超出的实体被截断丢弃。

### 关系词元数上限（max_relation_tokens，默认 8000）

关系描述部分最多占 8000 tokens（约 4000 汉字）。

### 总词元数上限（max_total_tokens，默认 30000）

整个上下文的总 token 预算。三者关系：

```
总预算 30000
  ├─ 实体描述: ≤ 6000
  ├─ 关系描述: ≤ 8000
  ├─ 原文片段: ≤ 16000 (30000 - 6000 - 8000)
  └─ 系统指令: ~2000
```

qwen3.6-flash 支持 128K 上下文，30000 只用了不到 1/4，安全。

## 重排（Rerank）

### 重排是什么

检索分两步走：

```
第一步：向量检索（粗筛）
  从图谱检索 60 个实体/关系 + 20 段原文
  -> 按向量相似度排序
  -> 但相似度高 ≠ 真正相关

第二步：重排模型（精排）
  用专门的 reranker 重新打分
  -> 按真正相关性重排序
  -> 扔掉不相关的，保留最相关的
```

**类比**：向量检索像"快速翻书找目录"，重排像"逐页精读确认相关性"。

### 当前状态

**未配置重排模型**。LightRAG 当前只做向量检索，不做精排。

### 如需启用

在 `/opt/lightrag.env` 添加：

```env
RERANK_BINDING=aliyun
RERANK_MODEL=gte-rerank-v2
RERANK_BINDING_HOST=https://dashscope.aliyuncs.com/api/v1/services/rerank/text-rerank/text-rerank
RERANK_BINDING_API_KEY=sk-cad2e2400e384fc7aa08846770dac9e1
```

然后 `docker compose up -d --force-recreate lightrag` 重建容器。

### 启用重排的代价

- 每次查询多一次 reranker API 调用（+1-2 秒延迟）
- 检索精度提升（减少不相关内容）
- 适合知识库文档多、检索噪声大时启用

## 参数默认值汇总

| 参数 | 默认值 | 说明 |
|---|---|---|
| 查询模式 | hybrid | 实体+关系双层检索 |
| KG Top K | 60 | 图谱检索数量 |
| Chunk Top K | 20 | 原文检索数量 |
| 实体词元数上限 | 6000 | 实体描述 token 预算 |
| 关系词元数上限 | 8000 | 关系描述 token 预算 |
| 总词元数上限 | 30000 | 上下文总 token 预算 |
| 重排 | 未启用 | 可选配 gte-rerank-v2 |
| 分块大小 | 1200 tokens | 文档切分粒度 |
| 分块重叠 | 100 tokens | chunk 间重叠 |
| 余弦阈值 | 0.2 | 向量相似度过滤 |

**当前配置适合教学场景，无需修改。**
